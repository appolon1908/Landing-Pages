# CRM intake boundary

CRM is the business authority; its vendor is unconfirmed. The intake service validates requests and routes them. It does not own matching, booking, provider activation, billing or a second business database. Every bundled registry remains preview with a disabled destination.

The v3 envelope has exactly one `request` or `application`, the consent intent and bounded attribution. The backend derives the site from Host, requires a configured HTTP Origin equal to the source-page origin, and validates the page against trusted deployed manifests and the site's market. It does not trust forwarded host/IP headers. Behind the page proxy, rate limiting therefore uses the observed proxy address and site; a future trusted-proxy deployment needs an explicit reviewed design before client IP forwarding can be trusted.

For the generic CRM webhook, configuration must explicitly declare `idempotencyContract: "site-key-payload"` before any forwarding. The receiving CRM must persistently deduplicate the site-scoped `Idempotency-Key`, reject changed content under that key, and return the same canonical record ID for a replay. The request includes a deterministic `requestId` trace UUID and a canonical `payloadFingerprint`. The trace is stable across intake retries and process restarts; it is not the CRM record ID. `receivedAt` is observation metadata and can differ after a retry.

A CRM acknowledgment must be JSON `{ "accepted": true, "id": "<canonical CRM receipt ID>" }`. The ID must be nonempty, at most 160 characters, and contain no control characters. Only this acknowledgment produces `downstream_status: "CRM_ACCEPTED"` and `crm_receipt_id`. The logging destination returns HTTP 202 with `status: "DELIVERY_LOGGED"`; this is only a transport acknowledgment and never business acceptance. Other non-CRM acknowledgments fail closed. The browser rejects a log acknowledgment, a missing ID or any other downstream status. It uses `request_id` for intake tracing and `crm_receipt_id` for the canonical CRM receipt. A received request is not a booking; a received application is not account activation.

The local idempotency map and optional journal are scaffolding, not durable exactly-once delivery. Transport failures can have an uncertain outcome. The error keeps the stable trace reference; retries must keep the same site-scoped key and content. A fake CRM test proves replay behavior across intake-memory reset only for the specified deduplication contract. No real CRM endpoint, persistent deduplication, operational reconciliation queue or recovery procedure has been verified. Production enablement requires those facts to be established by the owner; setting a configuration string alone is not evidence that a CRM implements the contract.

Turnstile is absent from all bundled registries. If later configured with environment-variable names, the server verifies the token and hostname before delivery. Secret values and tokens are never forwarded to the CRM. In-memory rate limits default to ten attempts per ten minutes per observed IP/site and return Retry-After; their bounded map is a local protection, not a distributed quota service.

UI attribution is captured from an allowlist into memory only. It does not copy form fields, files or unknown query keys. Allowed UTM values are bounded text, not automatically redacted; campaign operators must keep personal data out of them. Locale changes preserve entered fields and clear all consent choices whose displayed wording changed. Preview submission never performs a POST and never renders a receipt confirmation.

Provider profile details are optional and self-declared: service radius (0–500 km), job size, professional qualifications, quote process and commercial preferences. Text is bounded to 500 characters. Zones remain the matching-area authority; radius does not expand them. Preferences do not authorize charges. No document or photo upload is implemented; any future evidence collection requires a separate secure follow-up design.

The optional n8n transport signs exact body bytes using HMAC-SHA256 in `X-Breero-Signature: sha256=<hex>` and still requires the canonical CRM acknowledgment and deduplication contract. Odoo is an explicit unconfigured stub. Neither is selected by any bundled registry.

The legacy Breero public-submissions transport is unverified for v3. It now requires the same explicit idempotency contract, sends the site-scoped key and fingerprint, and accepts only a `CRM_ACCEPTED` acknowledgment with a validated `crm_receipt_id`. A legacy queued response or intake trace ID is insufficient. No legacy integration has been activated or tested against a live service. Webhook URL user information is prohibited; authentication values belong in the configured environment.
